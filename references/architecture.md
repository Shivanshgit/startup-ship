# Architecture Reference

Design before you write code. A week of architecture saves a month of refactoring.

---

## Step 1 — Data model

List every entity in the system. For each entity:

| Entity | Key fields | Relationships | Notes |
|--------|-----------|---------------|-------|
| User | id, email, created_at | has Profile, has Trips | auth.users in Supabase |
| Profile | user_id, name, bio, verified | belongs to User | public-readable |
| Trip | id, host_id, origin, destination, dates, status | belongs to User, has Requests | geo fields use PostGIS |
| Request | id, trip_id, requester_id, status, answers | belongs to Trip + User | mutual approval |
| Match | id, trip_id, user_a, user_b, confirmed_at | belongs to Trip | created after both approve |
| Message | id, match_id, sender_id, body, sent_at | belongs to Match | realtime |
| Review | id, reviewer_id, reviewee_id, trip_id, rating | belongs to User + Trip | post-trip only |
| Report | id, reporter_id, subject_id, reason, status | moderation queue | admin-only read |

**Rules for the data model:**
- Every table gets `id uuid default gen_random_uuid()`, `created_at timestamptz default now()`, `updated_at timestamptz`
- Soft-delete with `deleted_at` instead of hard delete for user-generated content
- Never store PII in a column that joins to a public table

## Step 2 — Row Level Security (Supabase/Postgres)

Every table needs RLS policies before any data is written. Define:

| Table | Who can read | Who can write | Notes |
|-------|-------------|---------------|-------|
| profiles | anyone | owner only | public discovery |
| trips | anyone (approximate location only) | host only | exact location hidden |
| requests | requester + host | requester (create), host (status update) | — |
| matches | both participants | system (auto-create on mutual approval) | — |
| messages | both match participants | sender only | — |
| reviews | anyone | reviewer, once per trip | no editing after submit |
| reports | admins only | reporter (create) | — |

**Location privacy pattern:**
```sql
-- Public: return bounding box, not exact point
create view public_trips as
  select id, ST_Buffer(location, 5000) as area, ...
  from trips where deleted_at is null;

-- After match confirmed: return exact point
-- Only accessible to match participants via RLS
```

## Step 3 — API surface

List what the frontend needs. Supabase generates REST + GraphQL automatically from the schema, plus you get typed queries via `supabase gen types`.

**Critical custom logic** (needs Edge Functions or server-side code, not auto-generated):

| Endpoint | Logic | Why not auto |
|----------|-------|--------------|
| `POST /requests` | Create request + notify host | Side effect: push notification |
| `PATCH /requests/:id/approve` | Mutual approval check → create Match | Atomic: both-approve before match |
| `POST /matches/:id/confirm` | Both confirm → unlock exact location | Conditional: requires chat happened |
| `POST /trips/:id/report` | Create report + flag for review | Rate limited, moderation queue |
| `POST /reviews` | Create review + update reputation | Only after trip completed |

Everything else (CRUD) is auto-generated by Supabase.

## Step 4 — Auth flow

```
Sign up
  → email/phone entered
  → OTP sent
  → OTP verified → session created
  → onboarding: profile created, preferences set
  → verification: document/video upload (async review)

Sign in
  → email/phone + OTP
  → session refreshed

Session
  → JWT stored in secure storage (not localStorage on web)
  → Refresh token auto-rotated by Supabase
  → RLS uses auth.uid() for all DB queries
```

**Never store the JWT in localStorage** — use `httpOnly` cookies on web, `flutter_secure_storage` on mobile.

## Step 6 — Scalability seams

For MVP, these are acceptable limits. Know them before you hit them:

| Constraint | Limit | When it matters |
|-----------|-------|-----------------|
| Supabase Realtime connections | ~200 concurrent (self-hosted, depends on RAM) | If you have 200+ active chats simultaneously |
| PostGIS radius queries | Fast up to ~1M rows with proper index | Never a problem for MVP |
| Meilisearch index size | Limited by RAM (self-hosted) | Add more RAM when index > 4GB |
| Supabase Storage | Limited by disk | Expand disk on Coolify |
| Push notifications (ntfy) | Unlimited self-hosted | Never a ceiling |

**The real scale bottleneck is almost never tech** — it's the core loop and retention. Don't over-engineer for scale before you have users.
